# Closed Alpha Program

Trip Service owns the closed-alpha program state: invite codes, waitlist entries,
participant metadata, product analytics events, feedback, and weekly reports.
Auth Service remains the source of truth for accounts and tokens; User Service
remains the source of truth for profile and workspace data.

## Invite Codes

Invite codes are generated by Ops and are stored as hashes. The raw code is only
returned once, in the response that creates the invite.

Invite fields:

- `codeDisplay`: safe prefix/suffix display value.
- `expiresAt`: optional expiration timestamp.
- `maxActivations` and `currentActivations`: support one-time and multi-use codes.
- `creatorUserId`: authenticated Ops user that created the invite.
- `notes`: short internal note.
- `testerGroup`: `internal`, `external`, `qa`, or `design_reviewer`.
- `enabled`, `createdAt`, `updatedAt`.

Activation uses `POST /alpha/activate` with an authenticated user and an invite
code. The backend locks the invite row while activating, rejects expired or
disabled codes, and creates or updates the matching `alpha_participants` row.

## Waitlist

The public waitlist endpoint is `POST /alpha/waitlist`. It stores a normalized
email for operational follow-up plus a hash for dedupe. Waitlist entries are not
automatically invited.

Statuses:

- `registered`
- `invited`
- `accepted`
- `declined`
- `removed`

Ops can list, filter, update, and invite waitlist entries from the alpha
dashboard.

## Participant Metadata

`alpha_participants` stores alpha-only metadata:

- tester group
- invitation date
- first login
- first trip
- first AI generation
- last activity
- active flag

It does not duplicate profile attributes, workspace memberships, preferences, or
credentials.

## Admin APIs

All Ops routes require the existing Ops authorization middleware.

| Method/path | Purpose |
| --- | --- |
| `GET /ops/alpha/invites` | List invite codes with safe display values |
| `POST /ops/alpha/invites` | Create an invite and return the raw code once |
| `PATCH /ops/alpha/invites/{inviteId}` | Update enabled flag, limits, notes, group, or expiration |
| `DELETE /ops/alpha/invites/{inviteId}` | Disable an invite |
| `GET /ops/alpha/waitlist` | List waitlist entries, optionally by status |
| `PATCH /ops/alpha/waitlist/{waitlistId}` | Update status or notes |
| `POST /ops/alpha/invite-from-waitlist` | Create an invite and mark a waitlist entry invited |
| `GET /ops/alpha/dashboard` | Read alpha health, funnel, feature usage, and alerts |
| `GET /ops/alpha/reports/weekly` | List generated weekly reports |
| `POST /ops/alpha/reports/weekly/generate` | Generate a human-readable weekly report |

## Abuse Controls

- Invite codes are random, hashed, and rate limited at activation.
- Waitlist registration is public but rate limited.
- Invite activation increments are performed inside a transaction.
- Ops-only actions stay behind the existing Ops admin middleware.
- No password, token, prompt, receipt, private note, or raw AI response data is
  stored in alpha analytics.
